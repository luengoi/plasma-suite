# 0002: Build iOS apps with Tuist

## Status

Accepted.

## Context

Plasma Suite will ship several iOS apps that share foundation modules, in the same repository as self-hosted services (see [0001](0001-use-a-single-repository.md)). The iOS codebase needs:

- No hand-maintained Xcode project files; generated ones are acceptable.
- Fast builds as the codebase grows.
- Targeted CI that runs only affected tests and reuses cached builds.
- Working SwiftUI Previews, for fast iteration while the design tokens and UI building blocks take shape.
- Tooling upkeep small enough for one maintainer.

Options considered in October 2026:

- **Bazel** (rules_apple, rules_swift, rules_xcodeproj) offers the strongest caching and test selection, one dependency graph for apps and services, and self-hostable remote caches. However, projects generated by rules_xcodeproj do not support SwiftUI Previews on current Xcode releases, new Xcode releases arrive through rule updates, and upkeep is the highest of all options.
- **Tuist** generates native Xcode projects, so Previews and new Xcode features work immediately. Selective testing and shared caching run through its hosted service; self-hosting requires an Enterprise license.
- **Xcode projects with local Swift packages**, or **XcodeGen**, leave targeted CI to custom scripts. Xcode 27.2's JSON project format eases diffs but still requires maintaining the project by hand.
- **Buck2** has little iOS use outside Meta.

## Decision

Use Tuist to generate the iOS workspace, and Xcode to build it. Generated project and workspace files are not committed.

### Structure

- `ios/apps/<App>/`: one directory per app, containing:
  - `App/`: the entry point and bundle resources, which hand off to the shell.
  - `Shell/`: root navigation, dependency wiring and app-wide state.
  - `Extensions/`: widgets and other app extensions.
  - `features/<Feature>/`: features owned by this app.
- `ios/foundation/<Module>/`: modules shared by all apps, such as the design system, networking, persistence and models.
- `ios/testing/`: test helpers shared across modules.

Each module has its own directory with `Sources/` and, as needed, `Resources/`, `Tests/`, `Interface/` and `DevApp/`.

### Dependency rules

- Dependencies point down: entry point, shell, features, foundation, then Apple frameworks and third-party packages.
- A feature reaches another feature of the same app only through that feature's `Interface` module, and never imports another app's features. When a second app needs a feature, its reusable part moves to foundation.
- Foundation modules never import features or shells.
- Test helper modules are imported only by tests and dev apps.
- Feature module names include their app's name, keeping Swift module names unique.
- Project description helpers define each module kind and reject disallowed dependencies.

### Keeping Bazel open

The layout stays portable to Bazel: one module per directory, all dependencies declared (CI checks for implicit imports), no custom build phases or run scripts, and resources kept in the module that uses them.

Re-evaluate Bazel every three months, or sooner when:

- rules_xcodeproj supports SwiftUI Previews natively;
- CI time or cost keeps growing despite selective testing;
- the services adopt Bazel, or cross-component change detection becomes necessary;
- Tuist's hosted service is no longer acceptable and CI without a shared cache is too slow.

### CI

CI runs on GitHub-hosted macOS runners; a self-hosted Mac is added only if CI time grows. Path filters skip iOS jobs for changes outside `ios/`. Tuist selective testing runs only affected test targets, and Xcode's compilation cache with Tuist's hosted cache reuses build work. The Tuist version is pinned.

## Consequences

- Previews and new Xcode features are available as soon as Xcode ships them.
- Test selection results and shared cache entries live in Tuist's hosted service, on its free plan: an accepted exception to self-hosting, for development tooling only.
- CI selects tests per test target and only within iOS; changes to contracts shared with services must run the CI of both.
- Before UI work starts, a setup phase must prove generation from a clean clone, Previews (including rendering through Xcode's MCP server), selective testing, the dependency rules and a TestFlight upload.
- A later move to Bazel replaces manifests and CI configuration, not the module layout.
